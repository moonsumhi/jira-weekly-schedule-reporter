# 월간 점검 작업 등록과 작업계획서 연결

## 사용 방법

- **서버 점검 → 월간 작업 → 작업 추가**에서 **스케줄 관리(이슈 가져오기)** 또는 **작업계획서(계획서 가져오기)**를 선택한다.
- 스케줄 관리의 기존 이슈는 그대로 연결한다. 필요한 경우 **새 이슈 만들기**도 사용할 수 있다.
- 작업계획서는 단일 검색 선택 필드에서 한 개를 골라 바로 점검 작업으로 등록한다. 다른 계획서를 선택하면 기존 선택을 교체하고 대상 서버·예정일을 다시 가져온다. 선택 개수나 다중 연결 목록을 표시하지 않으며, `내용 보기`로 원본을 확인한다. 별도의 이슈나 계획서 사본은 만들지 않는다. 계획서의 작업명·연결 자산을 가져오며, 작업일이 선택한 달에 있으면 예정일로 사용하고 그렇지 않으면 해당 월의 점검일을 제안한다. 대상 서버·담당자·예정일은 등록 전에 수정할 수 있다.
- 작업계획서에서 가져온 작업의 담당자는 백오피스 사용자 중 선택한다. 월별로 진행 상태·결과를 관리하며, **⋯ → 점검 작업 수정**에서 담당자·예정일·대상 서버를 변경한다. 제목을 누르면 원본 작업계획서가 팝업으로 열린다.
- 같은 계획서를 같은 달에 중복 등록할 수 없다. 다른 달에는 추가할 수 있고, 제외한 작업은 다시 등록할 수 있다. 자산 운영 이력과 점검 보고서에서도 확인할 수 있으며, 보고서 참여자의 담당 업무에도 자동으로 포함한다.

작업계획서를 작성하거나 수정하는 화면에서도 **서버 점검에 추가**를 선택할 수 있다.

- 점검 월·작업 예정일을 지정하고, 필요하면 백오피스 사용자 중 점검 담당자를 선택한다. 계획서에 연결한 서버를 그대로 사용하며, 서버 점검에 새로 추가하려면 대상 서버를 선택해야 한다.
- 작업일이 선택한 월에 있으면 예정일로 사용하고, 다른 월을 선택하면 해당 월의 점검일을 제안한다. Import한 계획서와 자산에서 연 문서 수정 팝업에도 같은 기능을 제공한다. 작업계획서 양식과 서버 점검 권한이 있는 사용자에게만 옵션을 표시한다.
- 해당 월에 계획서가 이미 연결된 점검 작업이 있으면 기존 등록 상태를 표시하고 추가 등록을 건너뛴다. 기존 작업의 상태·결과·대상 서버는 유지한다. 체크를 해제해도 이미 등록된 점검 작업을 삭제하지 않는다.
- 문서를 먼저 저장한 뒤 기존 점검 등록 API로 추가한다. 점검 등록만 실패하면 저장된 문서 ID와 버전을 유지하고 편집 화면에서 재시도할 수 있다. 등록 응답을 받지 못한 경우 실제 등록 여부를 다시 확인해 중복 등록을 방지한다.

기존 이슈에 참고할 계획서를 연결하는 기능도 유지한다.

- **서버 점검 → 월간 작업 → 작업의 ⋯ → 작업계획서 연결**에서 기존 계획서를 검색하고 선택한다. 여러 계획서를 연결하거나 해제할 수 있다.
- 작업명과 문서 종류로 검색하며, **선택한 서버의 계획서만 보기**로 같은 자산에 연결된 문서를 찾을 수 있다. 검색은 전체 문서를 대상으로 한 후 최대 30건을 표시한다.
- 작업 제목 아래에 표시되는 계획서 제목을 누르면 문서 팝업이 열린다. 닫으면 보던 월간 작업 목록과 조회 조건을 유지한다.
- 작업계획서 상세의 **서버 점검** 버튼에서 연결된 점검 월과 작업을 확인한다. 항목을 선택할 때만 해당 월간 작업으로 이동한다.
- 점검 보고서의 작업 목록에도 계획서 제목을 표시한다. 인쇄물에는 제목이 포함되며, 계획서 본문은 별도로 열어 확인한다.

## 작업계획서에서 직접 등록한 작업

- `inspection_tasks` 루트에 `source_type=WORK_PLAN`, `work_plan_id`를 저장한다. 문서 ID는 원본 계획서 ID에서 네임스페이스를 포함해 결정적으로 생성한다. 기존 API의 `issue_id`는 이 경우 점검 작업 ID이며 실제 PM 이슈를 가리키지 않는다. 기존 이슈 작업은 `source_type=ISSUE`로 조회된다.
- 등록에는 `server_check`와 `job` 권한이 필요하다. 등록된 점검 작업의 조회·상태·담당자·결과 편집은 서버 점검 권한을 따른다. 프로젝트 소속은 필요하지 않다. 원본 계획서 팝업은 작업 관리 권한이 필요하다.
- 월별 회차에는 계획서 요약, 담당자, 상태, 대상 자산, 예정일, 결과를 저장한다. 이월 시 새 회차를 만들고 원래 회차의 이력을 보존한다. 지난달 완료 작업의 상태와 담당 정보는 변경할 수 없다.
- 상태·담당자·예정일 변경은 `task_version`으로 동시 변경을 감지한다. 결과는 별도 결과 버전으로 보호한다. 삭제된 계획서도 저장된 점검 이력은 남는다.
- 보고서는 프로젝트가 없어도 계획서에서 등록한 작업을 포함한다. 계획서 담당자에게도 기존 점검일 알림을 적용한다.

## 기존 이슈에 추가로 연결한 계획서

- 연결은 이슈 전체가 아닌 `inspection_tasks.occurrences`의 월별 작업에 저장한다. 계획서 원본과 이슈 상태·내용은 연결 저장으로 변경하지 않는다. 계획서 하나를 여러 작업이나 여러 달에 연결할 수 있다.
- 회차의 `work_plans`는 문서 ID, 제목, 종류, 작업일, 문서 버전과 연결 자산을 보관한다. 본문과 이미지는 복제하지 않는다. 조회 시 현재 문서 정보도 제공한다.
- 연결 변경에는 `server_check`, `job`, 해당 이슈의 프로젝트 접근 권한이 필요하다. 관리자에게도 동일한 저장 규칙을 적용한다. 작업 조회와 역방향 조회는 기존 프로젝트 접근 범위를 따른다.
- 보고서는 기존 서버 점검 권한을 따른다. `job` 권한이 없는 사용자는 보고서의 계획서 제목을 볼 수 있지만 문서 열기와 연결 편집은 제공하지 않는다.
- 최대 20개를 연결할 수 있으며 문서 ID, 중복, 문서 종류와 삭제 여부를 검증한다. 삭제된 원본의 기존 연결은 제목을 남기고 확인 불가로 표시한다. 기존 연결의 유지·해제는 가능하다.
- `work_plans_version`과 기존 문서 버전 조건부 갱신으로 동시 변경을 보호한다. 충돌 시 선택을 유지하고 **최신 연결 불러오기**로 다시 확인할 수 있다.
- 이월 시 다음 회차에 연결을 복사한다. 이월·제외된 회차와 지난달 완료 회차의 연결은 변경할 수 없다. 제외 후 다시 등록할 때 계획서를 별도로 지정하지 않으면 기존 연결을 유지한다.
- 보고서는 작성 시 계획서의 제목·버전 등 연결 정보를 보관한다. 초안에서 최신 내용 불러오기를 해야 갱신되며, 확정된 보고서는 원본 변경·삭제 후에도 그대로 유지된다. 팝업으로 여는 계획서 본문은 현재 원본이다.

## 검증과 반영

- `tests/test_inspection_work_plans.py`: 직접 등록, 이슈 미생성, 자산 이력, 프로젝트 없는 사용자, 중복·동시 수정, 월별 완료 기록, 결과·이월·재등록, 삭제 문서, 담당자 알림과 기존 계획서 연결·검색을 임시 MongoDB 컬렉션으로 검증한다.
- `tests/test_monthly_inspection_reports.py`: 프로젝트 없는 계획서 작업의 보고서 포함, 참여자 업무 자동 연결, 결과 공유와 확정 보고서 보존을 검증한다.
- 프런트엔드 빌드 및 로컬 모의 API 브라우저 검사로 팝업 복귀, 검색 응답 순서, 충돌 복구, 자산 가져오기와 모바일 화면을 확인한다.
- 백엔드 시작 시 연결 조회 인덱스를 추가한다. 실행 중인 Docker 서비스에 반영하려면 백엔드와 프런트엔드 재빌드·재시작이 필요하다.
